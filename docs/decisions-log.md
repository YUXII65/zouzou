# 决策变更记录（历史）

> 这里只记**已经被推翻 / 废弃**的规则和它们被谁取代。现行规则看 [`product.md`](./product.md)、[`ai-pipeline.md`](./ai-pipeline.md)、[`runbook.md`](./runbook.md)、[`perf.md`](./perf.md)。
> 新条目往下加，写清「日期 + 原规则 + 为什么推翻 + 现在是什么」。

## 2026-09-11 · 首页 AI 用量看板

- 原规则：首页显示「今日 AI 用量 / token / 剩余次数」（`AiUsageCard`）。
- 推翻原因：用户明确「这个项目并不追求花多少 token」，这不是卖点。
- 现在：用量只作为后台配额与降级逻辑（`src/lib/ai-quota.ts`），用户可见指标一律不做。

## 2026-09-17 · 公开演示脚本

- 原规则：用 `scripts/start-public-demo.ps1` 起 SQLite 时代的公开演示。
- 推翻原因：数据库已迁到 Neon Postgres，该脚本把 `DATABASE_URL` 设成 `file:./public-demo.db`，整条路已经不通。
- 现在：脚本保留失效守卫，本地预览统一走 [`runbook.md`](./runbook.md) 的流程。

## 2026-09-27 · 任务状态按钮可以循环

- 原规则：任务状态按钮点一下在 待办 → 进行 → 完成 → 待办 之间循环。
- 推翻原因：完成之后再点回去会让「今天完成」的计数和分组失真。用户明确要求「完成不能点了」。
- 现在：完成是终态，按钮 `disabled`、点击直接 `return`。

## 2026-09-27 · 便利贴显示编号步骤

- 原规则：便利贴保留带编号的步骤。
- 推翻原因：编号会把连续动作读成清单，也让步骤数失控（曾出现 5-6 块）。
- 现在：不显示序号，步骤文本去掉 `1.` / `第一步` / `①` / `一、` 前缀，最多 3 个真实动作，顺序由卡片排列表达。

## 2026-10-01 · 用户自己选推进模式

- 原规则：首页有模式选择器，四种模式（智能 / 普通 / 长期 / 探索），选择存 `localStorage: next_step_work_mode`，显式选择以用户为准。
- 推翻原因：用户不该先给自己贴标签，模式应由 AI 从真实需求推断。
- 现在：`mode-picker.tsx` 已删除，`quick-capture.tsx` 不再传 `workMode`；模式在澄清收口后由 `judgeWorkMode` 判定。

## 2026-10-01 · 「探索不计数」「长期允许没有截止」

- 原规则：探索模式不计入推进中任务数；长期项目可以不设截止日期。
- 推翻原因：探索只要有任务并开始做就算启动；长期没有截止就无法按截止倒推阶段。
- 现在：三种模式都计数；长期必须有截止日期。

## 2026-10-01 · 用任务条数上限约束模式

- 原规则：普通 ≤2 / 长期 ≤3 / 探索 ≤2。
- 推翻原因：用户明确不接受这种硬卡点，模式应该靠结构区分。
- 现在：任务数由完成当前里程碑真正需要几个独立结果决定，不设固定条数。

## 2026-10-01 · 任务状态「告一段落」

- 原规则：探索任务可以「告一段落」。
- 推翻原因：那是把「没有终点」错误压到任务层的产物。任务永远是待办 / 进行 / 完成。
- 现在：没有终点只对探索的**项目层**成立。

## 2026-10-01 · 把探索理解成「先验证方向 / 买信息」

- 原规则：探索是「先验证方向」的一次性动作。
- 推翻原因：探索是没有终点的长期成长，被迫收口等于否定这个模式。
- 现在：探索 = 路径（台阶）+ 节奏，不设截止。

## 2026-10-01 · 首页日期面板与打卡统计

- 原规则：首页顶部日期面板保留日期 + 时钟，面板里放连续天数、近 7 天完成数、「你的推进闭环」卡；时钟点击在 12/24 小时制之间切换（`localStorage: next_step_hour12`）。
- 推翻原因：这些数字与「今天要做什么」无关，用户要求整块删掉。
- 现在：首页没有日期 / 日历框。`src/components/current-time.tsx`、`src/components/calendar-date-panel.tsx` 都还在仓库里但**没有挂载点**，不要接回首页。

## 2026-10-01 · 首页输入框宽度：max-w-3xl

- 原规则（两处记录互相冲突，同日写进文档）：一处写「卡片最宽 `max-w-3xl`」，一处写「与『今天要做』面板同宽、不要 `max-w-3xl`」。
- 判定依据：代码里没有 `max-w-3xl`——`src/app/page.tsx` 用 `<Panel>` 包 `AiTaskPlanner`，`quick-capture.tsx` 是 `w-full min-h-44`，布局容器 `src/app/layout.tsx` 是 `max-w-5xl`，所以实际渲染就是与面板同宽。
- 现在：按代码记为「与『今天要做』面板同宽，不额外加 `max-w-3xl`」。「改回 `max-w-3xl`」这个诉求没有落地依据，挂在 [`_open-questions.md`](./_open-questions.md)。

## 2026-10-01 · 工具页状态统计卡

- 原规则：`/tools` 工具页的状态统计卡用对应色系（待整理偏警示、未完成偏主色、已完成偏成功、复盘偏 AI 色）。
- 推翻原因：工具匣不再单独成页。
- 现在：`/tools` 302 到 `/files`，不再是导航里的页面。

## 2026-10-01 · 文件页的手动文件夹入口

- 原规则：文件页提供「新建文件夹」「放进一件事」「编辑文件夹」；`v3.6` 一度还保留一个低调的「删除文件夹」（展开区右侧小字灰色）。
- 推翻原因：文件夹是 AI 按模式分组的结果，用户手动建 / 删会和分组逻辑打架。
- 现在：上述入口全部不提供，新建只走首页 AI 流程。

## 2026-10-01 · 探索项目挂 Review 页面

- 原规则：探索项目展开区放一个「回看这个项目」入口 → `ReviewDraftGenerator`（带 `projectId`）→ 落到文件页渲染 `ReviewSaveForm`；为此给 `Review` 加可空 `projectId`，唯一索引改 `(userId, reviewDate, projectId)`。
- 推翻原因：复盘在探索模式里不该是独立页面或用户填写流程。
- 现在（2026-10-13 起）：探索推进是**任务事件驱动**的系统内部判断，不挂 Review 页面，新链路也不依赖 `Review` / `ReviewNextAction`。`Review` / `ReviewTask` / `ReviewNextAction` 的数据结构还在，但没有入口。

## 2026-10-12 · 把「翻译规则」和「提问规则」拆成两段

- 原规则：翻译规则和提问规则拆成两份 prompt / 两个 agent。
- 推翻原因：两者互相辅助、不是线性关系；拆开后模型会先猜一遍再问，还多花 30-60 秒。
- 现在：提问职责在第 1 段翻译 Agent 内部完成，翻译一边产出结构化语义一边决定还缺什么。

## 2026-10-12 · 让生成 Agent 在澄清阶段先跑一遍猜分叉

- 原规则：生成 Agent 在澄清阶段先跑一次，预判分叉。
- 推翻原因：架构搞反——生成 Agent 只在澄清收口之后才开工；实测还多花 30-60 秒。
- 现在：分叉由第 1 段翻译 Agent 排出，第 2 段只在收口后生成，不给候选。

## 2026-10-13 · A/B 作为默认问法

- 原规则：默认用「A 还是 B」问用户。
- 推翻原因：同一目标下的两个子问题、两个动作、顺序或工具都不该问用户，AI 自己选风险更高、反馈更快的一个。
- 现在：默认 AI 自己判断一条路，只问缺的事实 / 条件；A/B 只用于两个真正不同的现实目标或条件。

## 2026-10-13 · AI 设置放在首页

- 原规则：首页有「偏好设置」折叠区，AI 设置入口在首页（`ai-preferences.tsx`）。
- 推翻原因：设置属于账号层，不该占首页。
- 现在：`ai-task-planner.tsx` 已删掉该折叠区，也不再接收 `quotaManaged` / `serverAiConfigured`；AI 设置只在个人页（`ai-settings.tsx`），`ai-preferences.tsx` 保留但无挂载点。

## 2026-10-14 · 文件页 / 个人页的顶部标题区

- 原规则：文件页顶部显示「让想法，走成下一步 + 文件 + 日期」，个人页顶部显示「让想法，走成下一步 + 个人」。
- 推翻原因：底部导航已经表明当前位置，重复标题是噪音。用户批注「全部删掉」。
- 现在：`src/app/files/page.tsx`、`src/app/profile/page.tsx` 都不渲染 `PageHeader`；`PageHeader` 仍供 admin / tools 等页面使用。

## 2026-10-15 · tool-router 联网搜索

- 原规则：`src/lib/tool-router.ts` 决定「最新信息 / 价格 / 政策 → 联网搜索；用户给了网址 → 读页面；GitHub / 仓库 → 查仓库；API / 文档 → 查文档」。
- 推翻原因：普通模式 Agent 不接 Tool / MCP，系统并没有真的联网能力；写成「会去搜索」等于假装已经查到。
- 现在：需要外部信息时，让模型直接给出「查什么 / 去哪查 / 按什么标准判断」的可用结论，把「用户自行核实」写成动作。`tool-router.ts` 保留，但只做 kind 标签（none / search / read / github / docs），由 `task-contract.ts` 使用，不发起真实请求。

## 2026-10-15 · 三段 Agent 链作为生产主链

- 原规则：`CONTENT_GENERATION_SYSTEM_PROMPT` + `NORMAL_COMPOSE_SYSTEM_PROMPT_V1` 三段链是生产主链。
- 推翻原因：中间草案和候选方案对最终结果没有增益，还多一次模型调用。
- 现在：生产固定走两段链（翻译 → 方案）；三段链只作失败回退，`TWO_STAGE_AGENT_PLAN=false` 才显式切回。

## 2026-10-16 · 限制模型只能选某种 responseMode

- 原规则：`ANSWER_MODE_ENABLED` 开关同时承担「允许直答」和「切回旧链」；提示词里有「默认 action」「只有…才准选 answer」「不要选 answer」这类限制。
- 推翻原因：代码只是给 API 套一层「提示词的壳」，不该限制模型输出什么；一个开关担两个职责也导致互相打架。
- 现在：`responseMode`（answer / action / plan）由第 1 段翻译 Agent 自己判，都是正常结果、没有默认项；`ANSWER_MODE_ENABLED` 已删除，回答生成唯一实现在 `src/lib/agent-plan/content.ts` 的 `generateDirectAnswer`。

## 2026-10-16 · 便利贴里写「例外：…」

- 原规则：把 `fallback` 作为「例外：…」追加进便利贴。
- 推翻原因：用户明确「不用动不动便利贴里面写例外」，而且它正是步骤数膨胀的第 6 块来源。
- 现在：fallback 仍然生成、仍然入库，只是不进便利贴展示。

## 2026-10-16 · `executionSteps` 最多 5 条

- 原规则：`executionSteps` 最多 5 条，`fallback` 再追加成第 6 条，两个动作被摊成五六块。
- 推翻原因：便利贴读起来像清单，不像执行卡片。
- 现在：提示词要求通常 2-3 条、**最多 3 条**，同一个动作的准备和执行合并成一条；`safePlanTask` 和 `stickyPayloadFromDecisionCard` 都会把多余步骤合并进最后一块。

## 2026-10-16 · 澄清「默认上限 3 轮」

- 原记录：一处写「多轮，默认上限 3」，另一处写「最多 4 问、最少 2 问」。
- 判定依据：代码是 `maxQuestions` 夹在 ≤4（调用方传 4）、`minQuestions` 默认 2 且 `inbox-ai.ts` 显式传 2。文档里的「上限 3」没有代码依据。
- 现在：**最少 2 轮、最多 4 轮**，到上限强制收口；`responseMode === "answer"` 的问题不受「至少两轮」约束。

## 2026-10-16 · 阶段预览面板铺任务清单 + 「重新生成」

- 原规则：长期项目待确认阶段的「下一阶段」预览里铺 3 条任务的 `shortTitle + doneWhen`，右下角配「重新生成 / 进入下一阶段」两个按钮。
- 推翻原因：浏览器批注——任务清单要删（会把预告读成待办），「不要出现重新生成」（下一阶段该自动生成，不该让用户手点）。
- 现在：只留一句话总结 + 一个「进入下一阶段」；总结由服务端生成、页面自动补取。

## 2026-10-16 · 澄清确认成功后 router.refresh()

- 原规则：`InboxClarification.finish()` 在确认成功/直接回答/先收着之后立刻 `router.refresh()`。
- 推翻原因：这条 inbox item 此时已经不是 pending，refresh 会让父组件整块卸载 `InboxClarification`，本地 `confirmed` / `directAnswer` / `ignored` 三种完成态永远没机会渲染——表现为「自己刷新了，没有按钮」。回归门禁见 `scripts/lib/repo-invariants.test.mjs`。
- 现在：完成态留在卡片里（「已放进文件」+「查看」/ 直接答案 /「这条先收着」），用户点「查看」跳转时自然重新取服务端数据；确认后同时收起「去看看」，避免两个按钮并存。
## 2026-10-16 · 点「进入下一阶段」同步等模型

- 原规则：`confirmStagePreviewAction` 在新阶段创建后同步 `await generateLongtermStagePreview(...)`，保证新阶段一打开就带着下一阶段总结。
- 推翻原因：浏览器批注——「这个点击进入的按钮可以稍微快点出现吗，可以在用户空闲时段自动生成好下一阶段的，就不用等了」。同步调用会让每次点「进入下一阶段」都卡一次 5-7 秒的模型调用；而且到第 5 阶段（最后一个）时这次调用纯属浪费。
- 现在：改成 `after()` 在响应之后生成，且只在 `order + 1 < MAX_LONGTERM_STAGES` 时生成。实测点击到新阶段落地约 1.8 秒。门禁：`scripts/verify-explore-tracks.mjs` 的「进入下一阶段不被模型调用阻塞（< 5000ms）」。
## 2026-10-16 · 首页的阶段完成提醒卡 + 文件页空状态文案

- 原规则：首页在有待确认阶段时显示一张「「XX」这一阶段完成了 / 交付物原文 / 下一阶段 →」的提醒卡；文件页只要当前没有推进中的任务就显示「没有推进中的任务 / 写下想法时 AI 会把它拆成这里的任务。」。
- 推翻原因：浏览器批注——首页那张卡「删掉」；文件页的空状态在**任务已经全部做完**的项目里显示这句是错的（截了两处：普通项目「已完成 1」、长期项目「已完成 16」），要「换成已全部完成」。
- 现在：首页不放阶段提醒卡（阶段推进只在文件页）；文件页在「完成过任务、当前无推进中」时显示「已全部完成」，只有一件都没做过才提示去写想法。门禁：`scripts/verify-explore-tracks.mjs` 的三条空状态断言。
